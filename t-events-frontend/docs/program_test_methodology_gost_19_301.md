## Аннотация

Настоящий документ является программным документом "Программа и методика испытаний" для клиентской части информационной системы T-Events Frontend. Документ составлен с учетом требований ГОСТ 19.301-79 и определяет объект, цели, требования, состав, порядок и методы испытаний веб-приложения.

T-Events Frontend представляет собой веб-приложение на базе Next.js, React и TypeScript, предназначенное для работы участников мероприятий, стендеров и администраторов. Испытания проводятся для подтверждения готовности клиентской части к эксплуатации совместно с backend-сервисом T-Events и для проверки соответствия функций требованиям технического задания, API-контракту и программной документации.

## 1. ОБЪЕКТ ИСПЫТАНИЙ

### 1.1. Наименование программы

Объектом испытаний является клиентская часть информационной системы T-Events:

- полное наименование: T-Events Frontend;
- краткое наименование: клиентское веб-приложение T-Events;
- тип программы: веб-приложение;
- технологическая платформа: Next.js, React, TypeScript.

### 1.2. Область применения

Программа применяется для проведения мероприятий с игровыми заданиями, начислением баллов, получением призов по QR-коду и административным управлением мероприятиями.

Программа предназначена для следующих категорий пользователей:

| Категория пользователя | Роль в системе | Назначение |
| --- | --- | --- |
| Участник | `participant` | Регистрация, вход, выбор мероприятия и направления, прохождение игр, просмотр прогресса, получение QR-кода на приз |
| Стендер | `stander` | Проверка QR-кода участника, предварительный просмотр права на приз, подтверждение выдачи приза, просмотр выданных призов |
| Администратор | `admin` | Создание и настройка мероприятий, управление расписанием, направлениями, игровыми шаблонами, публикацией и архивированием |

### 1.3. Обозначение программы

Для целей настоящего документа программе присваивается обозначение:

```text
T-EVENTS-FRONTEND
```

Обозначение документа:

```text
T-EVENTS-FRONTEND-ПМИ
```

Версия испытуемой программы определяется по файлу `package.json`. На момент составления документа версия пакета указана как `0.1.0`.

### 1.4. Краткая характеристика программы

Программа реализует клиентский интерфейс для backend API T-Events. Основные маршруты приложения:

| Маршрут | Назначение |
| --- | --- |
| `/` | Главная страница приложения |
| `/events` | Список доступных активных мероприятий |
| `/events/current` | Текущее участие пользователя |
| `/events/{event_id}` | Карточка мероприятия |
| `/events/{event_id}/directions` | Список направлений мероприятия |
| `/events/{event_id}/directions/{direction_id}` | Карточка направления |
| `/events/{event_id}/directions/{direction_id}/games` | Список игр направления |
| `/events/{event_id}/directions/{direction_id}/games/{event_game_id}` | Игровая сессия |
| `/events/{event_id}/directions/{direction_id}/progress` | Прогресс участника по направлению |
| `/events/{event_id}/directions/{direction_id}/reward` | Получение QR-кода на приз |
| `/auth/login` | Вход пользователя |
| `/auth/register` | Регистрация пользователя |
| `/auth/vk/callback` | Обработка возврата VK OAuth |
| `/stander/scan` | Сканирование или ручной ввод QR-токена |
| `/stander/inventory` | Журнал выданных призов |
| `/admin/events` | Список мероприятий администратора |
| `/admin/events/{event_id}` | Управление выбранным мероприятием |

Программа не хранит постоянные бизнес-данные самостоятельно. Данные пользователей, мероприятий, направлений, игр, QR-кодов и выдач хранятся в backend-системе. На стороне клиента сохраняется access-токен авторизации; refresh-токен хранится backend-сервером в HttpOnly-cookie.

## 2. ЦЕЛЬ ИСПЫТАНИЙ

### 2.1. Основная цель

Целью испытаний является проверка корректности выполнения программой функций, изложенных в разделе "Требования к программе" документа "Приложение T-Events для участия в образовательных активностях с элементами геймификации. Техническое задание", и подтверждение пригодности программы к эксплуатации в составе информационной системы T-Events.

### 2.2. Частные цели

Испытания должны подтвердить:

- корректность установки зависимостей, статического анализа, автоматизированных тестов и сборки;
- работоспособность основных пользовательских сценариев участника, стендера и администратора;
- наличие функций, прямо заданных техническим заданием: начальная страница, выбор мероприятия, выбор направления, игры, прогресс, рейтинг участников, QR-код на приз, профиль участника, работа с резюме, административное управление мероприятиями и аналитикой;
- корректность интеграции с backend API по маршрутам `/api/v1`;
- правильную обработку успешных и ошибочных ответов backend-сервера;
- соблюдение правил авторизации и разграничения доступа по ролям;
- корректность валидации форм и пользовательских сообщений;
- пригодность интерфейса для использования на настольных и мобильных устройствах;
- соответствие программной документации фактическому поведению приложения.

### 2.3. Критерии приемки

Программа считается выдержавшей испытания, если выполнены следующие условия:

1. Команды `npm run lint`, `npm run test` и `npm run build` завершаются без ошибок.
2. Все обязательные контрольные примеры из раздела 6 и приложения А имеют результат "пройдено".
3. Пользовательские сценарии участника, стендера и администратора выполняются без блокирующих дефектов.
4. Ошибки backend API отображаются пользователю понятными сообщениями, не приводят к аварийному завершению интерфейса и не нарушают состояние авторизации.
5. Защищенные страницы недоступны пользователям без соответствующей роли.
6. Функции, указанные в техническом задании, либо реализованы и успешно проходят испытания, либо зафиксированы в протоколе испытаний как несоответствия.
7. Документация содержит сведения, достаточные для установки, запуска, эксплуатации и проведения повторных испытаний.

### 3.2. Требования к авторизации и доступу

Программа должна:

- разрешать публичный доступ к главной странице, списку активных мероприятий, страницам входа и регистрации;
- требовать авторизацию для прохождения игр, просмотра личного прогресса и получения QR-кода;
- допускать к стендерским операциям только пользователей с ролями `stander` или `admin`;
- допускать к административным операциям только пользователей с ролью `admin`;
- перенаправлять неавторизованного пользователя на страницу входа с сохранением безопасного обратного маршрута;
- запрещать использование внешних URL в параметрах возврата после входа;
- не возвращать пользователя обратно на страницы авторизации после успешного входа;
- корректно очищать или обновлять состояние access-токена при ошибке авторизации.

### 3.3. Требования к интеграции с backend API

Программа должна взаимодействовать с backend-сервисом по API-контракту, используя:

- базовый префикс `/api/v1`;
- JSON-формат запросов и ответов;
- envelope-структуру успешного ответа вида `{ "data": ... }`;
- envelope-структуру ошибочного ответа вида `{ "error": { "code": "...", "message": "..." } }`;
- заголовок `Authorization: Bearer <access_token>` для защищенных маршрутов;
- отправку cookie при вызове refresh endpoint;
- проксирование запросов через Next.js rewrites на backend origin, заданный переменной `BACKEND_API_ORIGIN`.

Минимально подлежат проверке следующие группы endpoint:

| Группа API | Назначение |
| --- | --- |
| `/auth/register`, `/auth/login`, `/auth/refresh`, `/me` | Регистрация, вход, восстановление сессии и получение текущего пользователя |
| `/auth/vk/start`, `/auth/vk/callback` | Интеграция с VK OAuth |
| `/events`, `/events/{event_id}`, `/events/{event_id}/directions` | Публичные сведения о мероприятиях и направлениях |
| `/events/{event_id}/directions/{direction_id}/games` | Список игр направления |
| `/games/{event_game_id}/sessions` | Запуск, продолжение и получение состояния игровой сессии |
| `/answers` | Отправка ответа на вопрос |
| `/reward-status`, `/reward-qr`, `/redemption` | Получение статуса приза и QR-кода |
| endpoint профиля участника | Получение персональной информации, истории участия, статистики и статусов призов |
| endpoint отправки резюме | Передача ФИО, контактных данных и ссылки или файла резюме |
| `/stander/redemptions/preview`, `/stander/redemptions` | Проверка и подтверждение выдачи приза |

| `/admin/events`, `/admin/game-templates`, `/admin/event-games` | Администрирование мероприятий и игр |
| endpoint административной аналитики и выгрузки | Получение участников, резюме, аналитических данных и файлов выгрузки |

### 3.4. Требования к обработке ошибок

Программа должна отображать понятные сообщения при следующих классах ошибок:

- некорректный запрос: `invalid_request`;
- отсутствие или истечение авторизации: `unauthorized`;
- недостаточность прав: `forbidden`;
- отсутствие ресурса: `not_found`;
- временная недоступность сервиса: `service_unavailable`;
- ошибка внешней интеграции: `bad_gateway`;
- внутренняя ошибка сервера: `internal_error`;
- конфликт бизнес-правил: `event_inactive`, `game_already_completed`, `session_not_active`, `reward_locked`, `already_redeemed`, `event_not_editable`, `publish_validation_failed` и другие коды, предусмотренные API-контрактом.

При ошибке сетевого запроса программа должна сообщать пользователю о невозможности подключиться к серверу и сохранять возможность повторить действие.

### 3.5. Требования к пользовательскому интерфейсу

Интерфейс должен:

- отображать состояния загрузки при ожидании данных;
- отображать пустые состояния при отсутствии мероприятий, направлений, игр или выдач;
- показывать сообщения валидации форм до отправки некорректных данных;
- обеспечивать понятные переходы между мероприятиями, направлениями, играми, прогрессом и призами;
- корректно работать при ширине экрана от 360 пикселей;
- не допускать наложения текста, кнопок, карточек и элементов форм;
- обеспечивать доступность основных действий с клавиатуры;
- использовать единообразные компоненты интерфейса для кнопок, полей ввода, карточек, бейджей, сообщений об ошибках и заголовков страниц.

### 3.6. Требования к надежности клиентской логики

Программа должна:

- не выполнять несколько одновременных refresh-запросов при параллельном получении нескольких ответов `401`;
- повторять защищенные запросы после успешного обновления access-токена;
- не отправлять ответ на вопрос в неверном формате для текущего типа игры;
- не ломать маршрут при некорректных или отсутствующих числовых идентификаторах;
- корректно обрабатывать завершенную игровую сессию, отсутствие следующего вопроса и уже выданный приз;
- корректно извлекать signed token из QR-данных или введенной вручную строки.
- сохранять выбранное мероприятие, направление и текущий прогресс при обновлении страницы;
- предоставлять возможность повторного запроса при сбое загрузки данных без полной перезагрузки страницы;
- предотвращать повторное получение QR-кода после выдачи приза;
- предотвращать повторную отправку одного и того же резюме без подтверждения.

### 3.7. Требования к временным характеристикам

Проверке подлежат следующие временные характеристики, заданные техническим заданием:

- время отклика интерфейса на действия пользователя без учета сетевых задержек должно составлять не более 200 мс;
- время первичной загрузки начальной страницы не должно превышать 3 секунд при среднем качестве интернет-соединения;
- время загрузки внутренних страниц, включая выбор мероприятия, страницу игр, профиль и административную панель, не должно превышать 2 секунд;
- сетевые запросы должны выполняться асинхронно без блокировки пользовательского интерфейса;
- при выполнении сетевых запросов должны отображаться индикаторы загрузки;
- обновление статистики пользователя после получения ответа сервера должно происходить не более чем за 1 секунду;
- генерация и отображение QR-кода после подтверждения данных сервером должны происходить не более чем за 500 мс;
- загрузка таблиц участников и аналитики должна занимать не более 3 секунд при количестве записей до установленного сервером лимита;
- применение фильтров и сортировок аналитических данных должно выполняться без перезагрузки страницы и занимать не более 1 секунды.

### 3.8. Требования к сборке и качеству кода

Программа должна:

- устанавливаться командой `npm ci`;
- проходить статическую проверку командой `npm run lint`;
- проходить автоматизированные тесты командой `npm run test`;
- собираться для production-режима командой `npm run build`;
- не содержать TypeScript-ошибок, препятствующих сборке;
- не содержать критических ошибок ESLint.

### 6.6. Проверка регистрации, входа и восстановления сессии

Проверяемые требования: программа должна обеспечивать регистрацию, вход и восстановление access-токена.

Метод испытания:

1. Открыть `/auth/register`.
2. Ввести корректные данные нового пользователя.
3. Отправить форму регистрации.
4. При необходимости выполнить вход на `/auth/login`.
5. Обновить страницу защищенного раздела.
6. Дождаться выполнения refresh-запроса.

Ожидаемый результат:

- при некорректном email, коротком пароле, пустом телефоне или неверном формате ФИО форма показывает сообщения валидации;
- при корректных данных регистрация завершается успешно;
- вход по email и паролю возвращает пользователя в целевой раздел;
- access-токен сохраняется в клиентском состоянии;
- при истечении access-токена программа вызывает `/api/v1/auth/refresh`, обновляет токен и повторяет защищенный запрос;
- при невозможности обновить токен пользователь переводится в неавторизованное состояние.

### 6.7. Проверка разграничения доступа по ролям

Проверяемые требования: программа должна соблюдать доступ по ролям `participant`, `stander`, `admin`.

Метод испытания:

1. Войти как участник.
2. Попытаться открыть `/stander/scan`.
3. Попытаться открыть `/admin/events`.
4. Войти как стендер.
5. Открыть `/stander/scan` и `/stander/inventory`.
6. Попытаться открыть `/admin/events`.
7. Войти как администратор.
8. Открыть `/admin/events` и `/stander/scan`.

Ожидаемый результат:

- участник не получает доступ к стендерским и административным страницам;
- стендер получает доступ к стендерским страницам, но не получает доступ к административным страницам;
- администратор получает доступ к административным функциям и может выполнять стендерские операции, если это разрешено backend-сервером;
- при отказе доступа отображается понятное сообщение или выполняется переход на разрешенную страницу.

### 6.8. Проверка сценариев участника

Проверяемые требования: участник должен иметь возможность выбрать мероприятие, направление и перейти к играм.

- список игр содержит название, описание, тип игры, максимальный балл, количество шагов и текущий статус;
- отображается сводка прогресса по направлению и пороги призов;
- при пустом списке отображается пустое состояние.

### 6.9. Проверка игровых сценариев

Проверяемые требования: программа должна поддерживать игры типов `question_answer` и `quiz`.

Метод испытания для `question_answer`:

1. В списке игр выбрать игру типа `question_answer`.
2. Нажать запуск или продолжение сессии.
3. Ввести текстовый ответ.
4. Отправить ответ.

Ожидаемый результат:

- приложение создает или продолжает сессию через backend API;
- отображается текущий вопрос;
- ответ отправляется в формате `{ "answer": { "text_answer": "..." } }`;
- после ответа отображается результат, обновленный прогресс и следующий вопрос либо завершение игры.

Метод испытания для `quiz`:

1. В списке игр выбрать игру типа `quiz`.
2. Запустить или продолжить сессию.
3. Выбрать вариант ответа.
4. Отправить ответ.

Ожидаемый результат:

- варианты ответа отображаются как список доступных опций;
- ответ отправляется в формате `{ "answer": { "option_id": number } }`;
- программа не отправляет одновременно `text_answer` и `option_id`;
- после завершения всех вопросов сессия получает статус `finished`, а интерфейс предлагает вернуться к списку игр или проверить приз.

### 6.10. Проверка получения QR-кода на приз

6. Сформировать QR-код.

Ожидаемый результат:

- до достижения порога отображается состояние "приз недоступен" или аналогичное сообщение;
- после достижения порога backend возвращает статус доступности приза;
- кнопка получения QR-кода становится доступной;
- программа вызывает endpoint выдачи QR и отображает QR-код, содержащий `signed_token`;
- при уже полученном призе отображается сообщение о невозможности повторной выдачи.

### 6.11. Проверка профиля участника

Проверяемые требования: участник должен иметь возможность открыть профиль, увидеть персональные данные, историю участия, статистику баллов, статусы получения призов и выполнить выход из сессии.

Ожидаемый результат:

- отображаются история участия, статистика баллов и статусы призов;
- при редактировании контактных данных изменения проходят валидацию и сохраняются;

### 6.12. Проверка отправки резюме

Проверяемые требования: участник должен иметь возможность отправить резюме или ссылку на резюме, а повторная отправка одного и того же резюме не должна приводить к дублированию данных без подтверждения.

### 6.13. Проверка сценариев стендера

Проверяемые требования: стендер должен проверять QR-код и подтверждать выдачу приза.

Ожидаемый результат:

- предварительный просмотр показывает мероприятие, участника, направление, тип приза, статус QR и сведения о повторной выдаче;

- выданный приз появляется в журнале выдач;
- повторная выдача по тому же QR-коду блокируется backend-сервером и отображается понятным сообщением.

Проверяемые требования: администратор должен управлять жизненным циклом мероприятия.

6. Сохранить изменения.

Ожидаемый результат:

- черновик создается через backend API;
- поля формы отображают сохраненные значения;
- пустые обязательные поля и неверные проценты показывают сообщения валидации;
- окончание мероприятия раньше начала блокируется.

Метод испытания направлений и игр:

1. Добавить направление к черновику.
2. Открыть список игровых шаблонов.
3. Подключить игровой шаблон к направлению.
4. Изменить конфигурацию количества вопросов и баллов.

Ожидаемый результат:

- направление добавляется к мероприятию;
- игровые шаблоны загружаются из backend API;
- конфигурация игры сохраняется;
- некорректная конфигурация отображает сообщение об ошибке.

Метод испытания публикации и архивирования:

1. Подготовить мероприятие к публикации.
2. Нажать публикацию.
3. Проверить статус мероприятия.
4. Для опубликованного, но не начавшегося мероприятия изменить расписание.
5. Архивировать мероприятие.

Ожидаемый результат:

- при невыполненных условиях публикации отображается список причин;
- при корректной конфигурации мероприятие получает статус published или active в зависимости от backend-логики;
- расписание опубликованного будущего мероприятия изменяется через специальный endpoint;
- архивирование меняет статус мероприятия на `archived`;
- повторные или запрещенные действия отображают сообщения `already_published`, `event_not_schedulable`, `already_archived`, `event_archived` либо их пользовательские аналоги.

### 6.16. Проверка временных характеристик

Проверяемые требования: программа должна соответствовать временным характеристикам, заданным техническим заданием.

Метод испытания:

1. Открыть приложение в браузере с включенными инструментами разработчика.
2. Измерить время первичной загрузки начальной страницы.
3. Измерить время открытия внутренних страниц: выбор мероприятия, список игр, профиль, административная панель.
4. Измерить время отклика интерфейса на нажатие кнопок и переключение направления без учета сетевой задержки.
5. Проверить наличие индикаторов загрузки при сетевых запросах.
6. После ответа сервера на игровой запрос измерить время обновления статистики пользователя.
7. После ответа сервера на запрос QR-кода измерить время отображения QR-кода.
8. В административной панели измерить время загрузки таблиц, применения фильтров и сортировок.

Ожидаемый результат:

- начальная страница загружается не более чем за 3 секунды;
- внутренние страницы загружаются не более чем за 2 секунды;
- интерфейс реагирует на локальные действия не более чем за 200 мс;
- сетевые запросы не блокируют интерфейс;
- во время загрузки отображаются индикаторы;
- статистика обновляется не более чем за 1 секунду после ответа сервера;
- QR-код отображается не более чем за 500 мс после ответа сервера;
- административные таблицы загружаются не более чем за 3 секунды при количестве записей до серверного лимита;
- фильтрация и сортировка аналитики выполняются не более чем за 1 секунду.

### 6.17. Проверка обработки ошибок API

Проверяемые требования: программа должна корректно отображать ошибки backend API.

Метод испытания:

1. На тестовом backend-стенде или mock-сервере инициировать ответы с кодами ошибок.
2. Проверить отображение сообщения на соответствующей странице.
3. Проверить, что пользователь может повторить действие или перейти к безопасному состоянию.

Контрольные ошибки:

| Код ошибки | Сценарий проверки | Ожидаемый результат |
| --- | --- | --- |
| `unauthorized` | Открытие защищенной страницы без токена или с истекшим токеном | Запуск refresh или переход на вход |
| `forbidden` | Открытие административной страницы участником | Сообщение об отсутствии доступа |
| `not_found` | Открытие несуществующего мероприятия | Сообщение о ненайденном ресурсе |
| `event_inactive` | Запуск игры в неактивном мероприятии | Сообщение о недоступности мероприятия |
| `game_already_completed` | Повторный запуск завершенной игры | Сообщение о завершенной игре |
| `invalid_answer_payload` | Отправка ответа в неверном формате | Сообщение о некорректном ответе |
| `question_already_answered` | Повторная отправка ответа | Сообщение о ранее данном ответе |
| `reward_locked` | Получение QR до порога | Сообщение о недоступности приза |
| `already_redeemed` | Повторная выдача приза | Сообщение о ранее полученном призе |
| `qr_expired` | Проверка истекшего QR | Сообщение об истечении QR-кода |
| `publish_validation_failed` | Публикация неполного мероприятия | Список причин, мешающих публикации |
| `service_unavailable` | Недоступность внешнего сервиса или VK OAuth | Сообщение о временной недоступности |
| `internal_error` | Внутренняя ошибка backend | Сообщение о серверной ошибке |

Ожидаемый результат:

- ни одна ошибка не приводит к белому экрану или аварийному завершению приложения;
- сообщение соответствует характеру ошибки;
- состояние формы, токена и маршрута остается предсказуемым.
