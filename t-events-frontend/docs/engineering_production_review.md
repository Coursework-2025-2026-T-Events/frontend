## Рекомендации по frontend

### 1. Синхронизировать API-типы с backend

Проблема: DTO сейчас описаны вручную в TypeScript. При изменении backend API frontend-типы могут разойтись с фактическим контрактом.

Рекомендации:

- Использовать OpenAPI как источник правды.
- Генерировать TypeScript-типы из `openapi.yaml`.
- Добавить CI-проверку, что OpenAPI-файл актуален.
- Для критичных сценариев добавить контрактные тесты.

Ожидаемый эффект: меньше расхождений между frontend и backend, проще поддерживать API при развитии проекта.

### 2. Добавить runtime-валидацию критичных API-ответов

Проблема: TypeScript проверяет типы только на этапе сборки, но не гарантирует, что backend вернул данные нужной формы.

Рекомендации:

- Использовать `zod` или аналог для runtime-валидации ответов в критичных сценариях.
- В первую очередь валидировать auth, reward QR, redemption preview, game session state.
- При ошибке формы ответа показывать контролируемое сообщение и логировать техническую ошибку.

Ожидаемый эффект: frontend устойчивее к несовместимым изменениям API и частично некорректным данным.

### 3. Формализовать auth state machine

Проблема: состояние авторизации распределено между token store, React Query, logout intent и страницами.

Рекомендации:

- Явно описать состояния: `unknown`, `anonymous`, `refreshing`, `authenticated`, `expired`.
- Централизовать переходы между состояниями.
- Проверить edge-cases: reload страницы, истекший refresh token, несколько вкладок, ручной logout.
- Для нескольких вкладок использовать `BroadcastChannel` или storage events.

Ожидаемый эффект: меньше нестабильных состояний авторизации и неожиданных редиректов.

### 4. Усилить обработку ошибок

Проблема: маппинг ошибок есть, но нет полноценной клиентской наблюдаемости.

Рекомендации:

- Подключить Sentry или аналог для client-side ошибок.
- Логировать необработанные ошибки React и ошибки API-контракта.
- Разделить ошибки валидации, доступа, сети и серверные ошибки на уровне UI-компонентов.
- Добавить тесты на `getErrorPresentation` для всех доменных кодов backend.

Ожидаемый эффект: проще диагностировать проблемы пользователей и регрессии после релизов.

### 5. Добавить e2e-тесты

Проблема: нет автоматизированного браузерного набора для основных сценариев.

Рекомендации:

- Использовать Playwright.
- Покрыть сценарии:
  - регистрация;
  - вход;
  - refresh сессии;
  - просмотр мероприятий;
  - выбор направления;
  - прохождение quiz;
  - прохождение question-answer;
  - генерация QR;
  - preview QR стендером;
  - подтверждение выдачи;
  - публикация мероприятия администратором.

Ожидаемый эффект: основные пользовательские сценарии будут проверяться перед релизом, а не только вручную.

## Рекомендации по backend

### 1. Реализовать server-side logout

Проблема: refresh token сейчас не хранится на сервере и не отзывается. Logout выполняется только на клиенте.

Рекомендации:

- Добавить таблицу refresh-сессий:
  - `id`;
  - `user_id`;
  - `jti`;
  - `expires_at`;
  - `revoked_at`;
  - `created_at`;
  - `user_agent`;
  - `ip`.
- Добавить `jti` в refresh token.
- При refresh проверять не только JWT-подпись, но и состояние refresh-сессии в БД.
- Добавить endpoint logout, который отзывает текущую refresh-сессию.
- Реализовать refresh token rotation.

Ожидаемый эффект: пользовательский выход становится настоящим серверным отзывом сессии, а украденный refresh token можно инвалидировать.

### 2. Добавить rate limiting

Проблема: операции авторизации, регистрации и проверки QR потенциально уязвимы к brute force и abuse.

Рекомендации:

- Ограничить частоту запросов на:
  - `POST /api/v1/auth/login`;
  - `POST /api/v1/auth/register`;
  - `POST /api/v1/auth/refresh`;
  - `POST /api/v1/stander/redemptions/preview`;
  - `POST /api/v1/stander/redemptions`.
- Использовать лимиты по IP и, где возможно, по user id / email.
- Возвращать `429 Too Many Requests`.

Ожидаемый эффект: ниже риск перебора паролей, злоупотребления refresh endpoint и массовой проверки QR-токенов.

### 3. Добавить audit log

Проблема: для production важно знать, кто выполнил критичное действие.

Рекомендации:

- Логировать административные действия:
  - создание мероприятия;
  - изменение мероприятия;
  - публикация;
  - архивирование;
  - изменение расписания;
  - назначение или изменение игры.
- Логировать действия стендера:
  - preview QR;
  - подтверждение выдачи;
  - отклоненная попытка выдачи.
- Хранить:
  - actor user id;
  - action;
  - entity type;
  - entity id;
  - timestamp;
  - request id;
  - краткий payload без секретов.

Ожидаемый эффект: можно расследовать спорные выдачи, ошибки администрирования и инциденты доступа.

### 4. Усилить транзакционность критичных операций

Проблема: операции выдачи приза и начисления баллов чувствительны к race condition.

Рекомендации:

- Проверить, что подтверждение выдачи выполняется атомарно:
  - проверка QR;
  - создание `reward_redemptions`;
  - перевод QR в `redeemed`;
  - отмена прочих активных QR.
- Использовать транзакцию и уникальные ограничения.
- Проверить конкурентный сценарий: два стендера одновременно подтверждают один QR.
- Проверить конкурентный сценарий: два ответа на один вопрос отправлены почти одновременно.

Ожидаемый эффект: меньше риск двойной выдачи и двойного начисления баллов.

### 5. Улучшить observability

Проблема: без логов, метрик и трассировки production-инциденты сложно диагностировать.

Рекомендации:

- Перейти на structured JSON logs.
- Включать request id, method, path, status, latency, user id при наличии.
- Добавить Prometheus metrics или аналог:
  - количество запросов;
  - latency;
  - количество ошибок по статусам;
  - количество auth failures;
  - количество reward redemptions.
- Разделить health endpoints:
  - liveness: процесс жив;
  - readiness: БД доступна, миграции применены.

Ожидаемый эффект: проще мониторить систему и быстрее находить причины отказов.

### 6. Формализовать миграции и deployment

Проблема: embedded migrations удобны для разработки, но в production лучше иметь управляемую процедуру миграций.

Рекомендации:

- Описать порядок применения миграций перед запуском новой версии.
- Добавить rollback/backup procedure.
- Добавить отдельную команду проверки миграций.
- Разделить миграции и запуск приложения, если deployment-процесс этого требует.

Ожидаемый эффект: меньше риск неуправляемого изменения схемы БД при релизе.

## Рекомендации по безопасности

### 1. Secret management

Рекомендации:

- Не хранить секреты в репозитории.
- Использовать secret storage окружения деплоя.
- Ротировать `JWT_SECRET` и `QR_SIGNING_SECRET` по процедуре.
- Для JWT-ключей рассмотреть `kid` и поддержку нескольких активных ключей на период ротации.

### 2. CSRF

Текущее состояние: frontend умеет добавить `X-CSRF-Token`, если видит cookie `csrf_token`, но backend-поддержка CSRF в текущем коде не обнаружена.

Рекомендации:

- Либо убрать CSRF-логику из frontend, если она не используется.
- Либо реализовать полноценную CSRF-защиту на backend.
- Особенно важно это для cookie-based refresh и небезопасных методов.

### 3. Cookies

Рекомендации:

- В production использовать `Secure=true`.
- Проверить `SameSite` в зависимости от схемы доменов frontend/backend.
- Убедиться, что refresh cookie имеет минимально необходимый path.
- Рассмотреть очистку refresh cookie при logout.

### 4. Password policy

Рекомендации:

- Зафиксировать минимальные требования к паролю.
- Добавить защиту от частых попыток входа.
- Не раскрывать, существует ли email, при ошибках login.
