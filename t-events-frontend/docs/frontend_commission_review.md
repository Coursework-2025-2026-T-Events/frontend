# Анализ frontend-части проекта T-Events для комиссии

Документ фиксирует сильные стороны frontend-части проекта и направления дальнейшего развития. Сильные стороны сформулированы как выполненные инженерные решения, которые демонстрируют профессиональный уровень проработки клиентской части. Стороны развития вынесены в другие направления, чтобы показать дальнейший потенциал продукта без дублирования уже реализованных доработок.

## Сильные стороны

### 1. API-контракт сделан источником истины

В проекте выстроен подход, при котором frontend не полагается на произвольные структуры данных, а работает с формализованным API-контрактом. Типы ответов и запросов синхронизируются с backend-контрактом, что снижает риск расхождений между клиентской и серверной частями.

Реализация включает разделение сгенерированных DTO и frontend domain models. Такой подход позволяет не смешивать транспортные структуры backend с внутренними моделями интерфейса и сохраняет гибкость клиентской архитектуры.

Для критичных API-ответов добавлена runtime-валидация через `zod`. Она закрывает ограничение TypeScript, который проверяет типы только на этапе разработки, но не гарантирует форму данных, реально пришедших от backend во время выполнения.

Валидацией покрываются наиболее важные сценарии:

- авторизация;
- refresh сессии;
- состояние игровой сессии;
- отправка ответа;
- проверка доступности награды;
- генерация QR;
- preview и confirm выдачи приза;
- административные настройки мероприятия.

Это повышает устойчивость frontend к несовместимым изменениям backend и позволяет обрабатывать contract mismatch как контролируемую ошибку, а не как случайный runtime-сбой.

### 2. Auth model усилена до явной state machine

Авторизация оформлена не как набор разрозненных условий, а как явная модель состояний сессии. Это делает поведение приложения предсказуемым в сложных сценариях, где одновременно участвуют access token, refresh cookie, React Query cache, logout intent и защищенные маршруты.

Модель описывает основные состояния:

- `unknown`;
- `refreshing`;
- `anonymous`;
- `authenticated`;
- `expired`;
- `logout_in_progress`.

Такое разделение помогает явно контролировать переходы между состояниями: первичная загрузка приложения, успешный refresh, истечение access token, истечение refresh token, ручной выход пользователя, ошибка восстановления сессии и повторный вход.

Отдельно обработаны edge cases:

- reload страницы;
- истекший access token;
- истекший refresh token;
- несколько открытых вкладок;
- ручной logout;
- параллельные `401` ответы;
- защита маршрутов по ролям.

### 3. Добавлен полноценный e2e-слой

В проекте настроен e2e-контур на Playwright, который проверяет не только отдельные функции, но и ключевые пользовательские сценарии в браузере.

E2E smoke suite покрывает основные маршруты продукта:

- регистрация;
- вход;
- восстановление сессии через refresh;
- выбор мероприятия;
- выбор направления;
- прохождение игры;
- генерация QR-кода;
- сканирование QR-кода стендером;
- подтверждение выдачи приза;
- создание и публикация мероприятия администратором.

### 4. Добавлена frontend observability

В проекте реализована клиентская наблюдаемость для ошибок, которые сложно диагностировать только по жалобам пользователей или backend-логам. Frontend фиксирует критичные сбои интерфейса и технические ошибки, сохраняя при этом безопасность пользовательских данных.

Observability покрывает:

- runtime UI crashes;
- API contract mismatch;
- неожиданные API-ошибки;
- ошибки QR-сканера и камеры;
- failed critical mutations;
- сбои в auth flow;
- ошибки при генерации или проверке QR.

Для пользовательского интерфейса и технической диагностики используются разные уровни сообщений. Пользователь видит безопасную и понятную формулировку, а разработчик получает контекст, достаточный для расследования.

При логировании учитываются ограничения безопасности: в события наблюдаемости не передаются access token, refresh token, QR signed token, redeem-коды и персональные данные сверх необходимого минимума.

### 5. Формализована дизайн-система

UI-примитивы проекта доведены до уровня формализованной дизайн-системы. Интерфейс строится не из случайных наборов CSS-классов, а из согласованных компонентов, вариантов и визуальных правил.

В дизайн-системе зафиксированы:

- design tokens для цветов;
- типографика;
- spacing;
- радиусы;
- состояния интерактивных элементов;
- единые `variant` и `size` API для компонентов;
- правила отображения ошибок, loading и empty states;
- доступные состояния форм;
- визуальные паттерны для административных и пользовательских экранов.

Для компонентов подготовлен каталог, который позволяет быстро просматривать состояния интерфейса и переиспользовать готовые элементы при развитии проекта. Это снижает вероятность визуальных расхождений между страницами и ускоряет добавление новых сценариев.

Также добавлена visual regression-проверка для ключевых экранов. Она помогает обнаруживать случайные изменения интерфейса, которые могут пройти незамеченными при обычном unit-тестировании.

### 6. Усилена проверка текстовой гигиены

В проекте реализован автоматический контроль текстовой гигиены, который проверяет исходники, документацию и пользовательские строки на признаки mojibake и поврежденной кодировки.

Ранее риск заключался в том, что поврежденные русские строки могли попасть в интерфейс или документацию. Теперь этот риск закрыт отдельным quality gate: проверка запускается командой `check:text` и входит в общий процесс контроля качества.

Проверка охватывает:

- `src`;
- `tests`;
- `docs`;
- `README.md`;
- служебные Markdown-файлы проекта.

Это важно для проекта с русскоязычным интерфейсом: корректность текстов влияет не только на внешний вид, но и на доверие к приложению. Автоматическая проверка не дает случайным поврежденным строкам закрепиться в репозитории и делает качество пользовательских сообщений контролируемым.

## Стороны развития

### 1. Продуктовая аналитика и измеримость пользовательских сценариев

Следующим направлением развития может стать внедрение продуктовой аналитики для ключевых действий пользователя:

- регистрация;
- вход;
- выбор мероприятия;
- выбор направления;
- старт игры;
- завершение игры;
- генерация QR-кода;
- сканирование QR-кода;
- подтверждение выдачи приза;
- публикация мероприятия администратором.

Это позволит оценивать не только техническую работоспособность приложения, но и реальную эффективность пользовательских сценариев. 

### 2. UX-исследование сложных сценариев

Проект содержит несколько ролей с разными задачами: участник, стендер и администратор. Для дальнейшего развития полезно провести отдельную UX-проверку этих сценариев, особенно для действий, которые пользователь выполняет в условиях ограниченного времени.

Особого внимания требуют:

- настройка мероприятия администратором;
- публикация мероприятия;
- добавление направлений и игр;
- сканирование QR-кода стендером;
- ручной ввод redeem-кода;
- обработка ошибок камеры;
- подтверждение выдачи приза.

По итогам UX-проверки можно улучшить навигацию, порядок действий, подсказки, визуальные акценты и обработку нештатных ситуаций.

### 3. Performance budgets и контроль клиентского bundle

Для дальнейшего роста проекта стоит добавить контроль размера клиентского JavaScript и performance budgets для основных маршрутов. Это особенно важно для страниц с QR-сканером, административными панелями и игровыми сценариями.

Потенциальные улучшения:

- анализировать размер bundle после сборки;
- отслеживать рост клиентского JavaScript в CI;
- lazy-load тяжелые части интерфейса;
- отдельно контролировать страницы QR-сканера и admin-раздела;
- проверять Core Web Vitals на ключевых маршрутах.

Такой подход позволит сохранить быструю загрузку приложения на мобильных устройствах и при нестабильном соединении.

### 4. Расширение сценариев offline и degraded mode

Для event-приложения важны мобильные устройства, нестабильная сеть и работа непосредственно на площадке мероприятия. Поэтому перспективным направлением является развитие graceful degradation.

Можно доработать:

- понятные состояния при потере сети;
- повтор критичных запросов;
- восстановление после временной ошибки backend;
- сохранение черновиков действий администратора;
- fallback для QR-сценариев;
- более явное восстановление после ошибки камеры;
- подсказки для ручного ввода кода при невозможности сканирования.

Это повысит надежность приложения в реальных условиях мероприятия, где сеть и устройства могут вести себя непредсказуемо.

### 5. Административный audit trail на уровне интерфейса

Для административных действий полезно добавить отображение истории изменений. Даже если основная audit-логика находится на backend, frontend может предоставить удобный интерфейс просмотра этих данных.

Полезно отображать:

- кто создал мероприятие;
- кто изменил расписание;
- кто обновил настройки игр;
- кто добавил или удалил направление;
- кто опубликовал мероприятие;
- кто архивировал мероприятие;
- когда именно было выполнено действие.

Такой audit trail повысит прозрачность административной работы и упростит разбор спорных ситуаций.

### 6. Расширение документации сопровождения

Помимо проектной и пользовательской документации стоит добавить frontend runbook для разработчиков, которые будут сопровождать проект после защиты.

В такой документации можно описать:

- как добавить новый API endpoint;
- как добавить новую страницу;
- как добавить новую роль;
- как добавить новый тип игры;
- как добавить новый UI-компонент;
- как добавить новый backend error code;
- как писать тесты для новой бизнес-логики;
- как проверять проект перед релизом.

Это снизит зависимость проекта от неформальных знаний конкретного разработчика и сделает кодовую базу проще для передачи другой команде.

### 7. Расширенная безопасность пользовательских сценариев

Дополнительным направлением развития является security review frontend-сценариев, связанных с чувствительными данными.

Особого внимания требуют:

- access token;
- refresh-сессия;
- QR signed token;
- redeem-код;
- персональные данные участников;
- ошибки backend;
- параметры redirect после авторизации;
- данные, которые могут попасть в URL, логи или сообщения об ошибках.

Можно добавить security checklist для code review и автоматические проверки, чтобы чувствительные данные не попадали в логи, публичные URL, диагностические сообщения или сторонние системы наблюдаемости.
