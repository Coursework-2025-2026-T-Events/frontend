# Рекомендации по улучшению инженерных и архитектурных решений T-Events

## Краткая оценка

Текущие решения выглядят сильными для курсового проекта, демонстрационного стенда и MVP: есть разделение frontend/backend, единый API-клиент, типизация на клиенте, слоистая архитектура backend, репозитории, PostgreSQL, миграции, JWT-аутентификация, ролевой доступ и базовые тесты.

До production-стадии проект пока не дотягивает. Основные причины: недостаточная зрелость security-механизмов, отсутствие полноценного server-side logout и отзыва refresh token, ограниченная наблюдаемость, неполная эксплуатационная упаковка, недостаток интеграционных и end-to-end тестов, а также ручная синхронизация API-контракта между backend и frontend.

Ориентировочная оценка:

- архитектура в целом: 7.5/10;
- frontend: 6.5/10;
- backend: 7/10;
- безопасность: 4.5/10;
- наблюдаемость и эксплуатация: 3.5/10;
- тестирование: 5/10;
- готовность к учебной защите и демонстрации: высокая;
- готовность к production: недостаточная.

## Сильные стороны

### Frontend

- Используется Next.js, React и TypeScript, что подходит для веб-клиента с маршрутизацией и интерактивными сценариями.
- Есть единый API-клиент, который централизует HTTP-запросы, JSON-обработку, cookie, access token, refresh token и преобразование ошибок.
- Access token хранится в памяти приложения, а не в `localStorage`, что снижает риск долговременного хранения токена в браузере.
- Используется TanStack React Query для серверного состояния, загрузок, ошибок, кэширования и мутаций.
- Есть отдельный слой API-функций по фичам, что отделяет страницы интерфейса от конкретных HTTP-маршрутов.
- Ошибки API преобразуются в пользовательские сообщения, а не показываются пользователю в техническом виде.

### Backend

- Используется понятная слоистая архитектура: HTTP-слой, прикладные сервисы, репозитории, инфраструктурные модули.
- Выбор Go, `net/http`, chi, `database/sql` и PostgreSQL хорошо подходит для предсказуемого REST API.
- Ручные SQL-запросы оправданы для проекта, где важны транзакции, ограничения целостности и явный контроль бизнес-операций.
- Есть миграции базы данных и учет примененных миграций.
- Ролевое разграничение вынесено на backend, а не доверено только frontend.
- Для QR-кодов используется подписанный JWT и запись в базе данных, то есть QR-токен проверяется не только криптографически, но и по состоянию предметной области.

## Почему это еще не production

### Безопасность

Главный production-риск связан с refresh token. Сейчас logout фактически клиентский: frontend очищает access token и локальное состояние, но сервер не хранит refresh-сессии и не может отозвать конкретный refresh token до истечения срока действия.

Для production нужно реализовать server-side logout: сервер должен хранить refresh-сессии или идентификаторы refresh token, уметь помечать их отозванными и отклонять дальнейшее обновление access token после выхода пользователя.

Также не хватает:

- refresh token rotation;
- отзыва refresh token при logout;
- защиты от brute force на login/register/refresh;
- rate limiting для чувствительных операций;
- аудита действий администратора и стендера;
- полноценной CSRF-стратегии, если refresh token живет в cookie;
- политики ротации секретов JWT и QR-токенов;
- контроля подозрительных повторных попыток выдачи призов.

### Наблюдаемость и эксплуатация

Для production недостаточно просто запускать приложение. Нужны средства, которые позволяют понять, что происходит с системой после выката.

Не хватает:

- структурированных JSON-логов;
- request id во всех логах и ошибках;
- метрик HTTP-запросов, ошибок, задержек, операций выдачи призов;
- readiness endpoint, который проверяет доступность PostgreSQL и состояние миграций;
- liveness endpoint для проверки живости процесса;
- алертинга по 5xx, задержкам, ошибкам БД и всплескам отказов авторизации;
- понятного процесса деплоя backend;
- общего Docker Compose или аналогичного сценария для frontend, backend и БД;
- backend Dockerfile;
- описанного процесса backup/restore PostgreSQL.

### Тестирование

Текущего уровня тестов достаточно для учебной проверки, но недостаточно для уверенного production-релиза.

Нужно добавить:

- интеграционные тесты backend с реальной PostgreSQL;
- тесты транзакционных сценариев выдачи призов;
- тесты конкурентных запросов на redemption;
- тесты повторного ответа на вопрос;
- тесты повторного запуска завершенной игровой сессии;
- тесты публикации неподготовленного мероприятия;
- end-to-end тесты в браузере для ключевых пользовательских сценариев;
- тесты API-клиента frontend на refresh flow, повтор запроса после `401`, logout intent и гонки нескольких запросов.

### API-контракт

Сейчас frontend-типы описаны вручную. Это нормально для небольшого проекта, но на production это риск рассинхронизации frontend и backend.

Лучше сделать OpenAPI-контракт источником истины и генерировать из него:

- TypeScript-типы для frontend;
- клиентские DTO;
- документацию API;
- часть проверок или моков для тестов.

### CSRF

Frontend уже предусматривает передачу `X-CSRF-Token`, если найден cookie `csrf_token`, но в backend должна быть реализована соответствующая проверка. Иначе это выглядит как незавершенное архитектурное решение.

Варианты:

- реализовать CSRF-защиту полностью;
- убрать упоминание CSRF из клиента и документации до фактической реализации;
- оставить CSRF как явно запланированное улучшение, но не описывать как уже готовую production-защиту.

## Нужно ли было использовать ORM

Использовать ORM было необязательно. Для текущего backend отказ от ORM выглядит разумным решением.

Причины:

- в проекте много предметных ограничений, которые удобнее явно выражать SQL-запросами и ограничениями PostgreSQL;
- сценарии выдачи призов, QR-токенов и игровых результатов требуют аккуратных транзакций;
- Go хорошо сочетается с явным `database/sql`;
- ORM не делает систему автоматически production-ready;
- ORM мог бы скрыть важные запросы и усложнить контроль транзакционного поведения.

Что стоит сделать вместо внедрения ORM:

- держать SQL только в repository-слое;
- покрыть репозитории интеграционными тестами;
- явно документировать транзакционные границы;
- проверять индексы и планы тяжелых запросов;
- использовать code generation для SQL при необходимости, например sqlc, если ручное сканирование строк станет слишком шумным.

ORM можно рассмотреть только если появится много однотипного CRUD, сложная административная модель и команда будет готова принять ограничения выбранного инструмента. Для текущей предметной области ручной SQL остается нормальным выбором.

## Что улучшить в первую очередь

### 1. Усилить auth и logout

Реализовать таблицу refresh-сессий, например:

- `id`;
- `user_id`;
- `token_jti`;
- `created_at`;
- `expires_at`;
- `revoked_at`;
- `user_agent`;
- `ip_address`.

После этого:

- добавлять `jti` в refresh token;
- проверять `jti` при refresh;
- отзывать refresh-сессию при logout;
- делать refresh token rotation;
- отклонять повторное использование старого refresh token;
- добавить endpoint `POST /api/v1/auth/logout`.

### 2. Добавить rate limiting

Минимально защитить:

- `POST /api/v1/auth/login`;
- `POST /api/v1/auth/register`;
- `POST /api/v1/auth/refresh`;
- `POST /api/v1/stander/redemptions`;
- `POST /api/v1/stander/redemptions/preview`.

Ограничения можно делать по IP, user id, email и QR-токену в зависимости от сценария.

### 3. Проверить транзакционность критичных операций

Особенно важно для выдачи приза:

- создание записи о выдаче;
- перевод QR-токена в `redeemed`;
- отмена других активных QR-токенов пользователя в рамках мероприятия;
- запрет повторной выдачи одному пользователю в рамках одного мероприятия.

Все это должно выполняться атомарно в одной транзакции.

### 4. Ввести аудит действий

Для production нужны audit logs:

- кто создал или изменил мероприятие;
- кто опубликовал или архивировал мероприятие;
- кто изменил игровую конфигурацию;
- кто проверил QR-токен;
- кто подтвердил выдачу приза;
- когда и с какого IP выполнено действие.

Это важно не только для отладки, но и для разбора спорных ситуаций на мероприятии.

### 5. Добавить интеграционные тесты backend

Нужны тесты с реальной PostgreSQL, потому что ключевые гарантии проекта находятся именно на уровне БД и транзакций.

Проверить:

- миграции применяются на пустой БД;
- уникальные ограничения работают;
- повторная выдача приза невозможна;
- повторный ответ на вопрос невозможен;
- завершенная игровая сессия не запускается повторно;
- публикация неподготовленного мероприятия отклоняется;
- leaderboard корректно считает позиции.

### 6. Добавить e2e smoke suite

Минимальный набор сценариев Playwright:

- регистрация и вход;
- обновление сессии после истечения access token;
- выбор мероприятия и направления;
- прохождение игры;
- получение reward status;
- генерация QR-кода;
- preview QR стендером;
- подтверждение выдачи;
- невозможность повторной выдачи;
- создание и публикация мероприятия администратором.

### 7. Сделать OpenAPI источником истины

Нужно описать API-контракт и подключить генерацию TypeScript-типов.

Это уменьшит риск, что backend возвращает одно поле, а frontend ожидает другое. Особенно важно для:

- auth DTO;
- event DTO;
- game session DTO;
- reward status DTO;
- QR preview DTO;
- redemption DTO;
- admin DTO.

### 8. Улучшить frontend auth state

Сейчас стоит явно оформить состояние авторизации как state machine:

- `unknown`;
- `anonymous`;
- `refreshing`;
- `authenticated`;
- `expired`;
- `logout_in_progress`.

Это сделает поведение интерфейса более предсказуемым при перезагрузке страницы, истечении access token, ошибке refresh и logout.

### 9. Синхронизировать logout между вкладками

Если пользователь открыл несколько вкладок, выход в одной вкладке должен приводить к выходу в остальных.

Для этого можно использовать:

- `BroadcastChannel`;
- storage events;
- общий auth provider, который слушает событие logout.

### 10. Добавить наблюдаемость

Минимальный production-набор:

- structured logging;
- request id;
- HTTP metrics;
- DB latency metrics;
- счетчики успешных и ошибочных redemption;
- счетчики auth failures;
- Sentry или аналог для frontend-ошибок;
- алерты на рост `5xx` и ошибок БД.

### 11. Упаковать развертывание

Для production или хотя бы staging стоит добавить:

- backend Dockerfile;
- общий compose-файл для frontend, backend и PostgreSQL;
- `.env.example` для frontend и backend;
- healthcheck для контейнеров;
- инструкцию миграции БД;
- инструкцию backup/restore.

## Приоритетный roadmap

### Ближайший минимум

1. Добавить server-side logout и хранение refresh-сессий.
2. Добавить rate limiting на auth и redemption.
3. Покрыть транзакции выдачи призов интеграционными тестами.
4. Добавить Playwright smoke-тесты основных сценариев.
5. Реализовать structured logs и request id.

### Следующий этап

1. Сделать OpenAPI-контракт источником истины.
2. Генерировать frontend-типы из OpenAPI.
3. Добавить backend Dockerfile и общий compose.
4. Добавить readiness/liveness endpoints.
5. Реализовать аудит действий администратора и стендера.

### Перед реальным production

1. Провести security review auth, cookie, JWT, CSRF и QR-токенов.
2. Провести нагрузочную проверку API и PostgreSQL.
3. Проверить планы запросов leaderboard и списков выдач.
4. Настроить мониторинг, алерты и backup/restore.
5. Подготовить runbook для инцидентов на мероприятии.

## Итог

Текущая архитектура выбрана в целом правильно. Главный вывод: проект не нужно переписывать и не нужно срочно переводить на ORM. Основной фокус должен быть не на смене технологического стека, а на production-дисциплине вокруг уже выбранных решений: безопасность сессий, транзакционные гарантии, тесты, наблюдаемость, деплой и единый API-контракт.
