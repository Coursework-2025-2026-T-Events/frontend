# T-Events Frontend

Клиентская часть приложения **T-Events** - веб-интерфейс для сопровождения образовательных и профориентационных мероприятий с элементами геймификации.

Приложение позволяет участникам выбирать мероприятие и направление, проходить игровые задания, отслеживать прогресс и получать QR/redeem-код награды. Для сотрудников стойки реализован сценарий проверки и подтверждения выдачи приза, а для администратора - интерфейс настройки и публикации мероприятий.

## Назначение проекта

T-Events решает задачу цифрового сопровождения интерактивных мероприятий. В ручном процессе организаторам сложно отслеживать прогресс участников, контролировать готовность мероприятия к запуску и предотвращать ошибочную или повторную выдачу призов.

Frontend-часть выступает связующим уровнем между пользователем, бизнес-процессом мероприятия и backend API. Она не только отображает данные, но и координирует состояние пользовательского пути: участие, игровые сессии, прогресс, получение награды, проверку выдачи и административное управление.

## Основные пользовательские роли

### Участник

Участник проходит основной пользовательский путь:

- просматривает каталог мероприятий;
- выбирает мероприятие и направление;
- видит список доступных игр;
- проходит игровые задания;
- отслеживает прогресс по направлению;
- получает QR/redeem-код при достижении порога награды.

### Стендист

Стендист отвечает за проверку и выдачу награды:

- сканирует QR-код или вводит redeem-код вручную;
- видит предварительную информацию о праве на получение награды;
- подтверждает выдачу приза;
- просматривает состояние выдач и инвентаря.

### Администратор

Администратор управляет мероприятием:

- создает и редактирует мероприятия;
- настраивает направления;
- управляет игровыми заданиями;
- проверяет готовность мероприятия к публикации;
- публикует или архивирует мероприятие;
- просматривает журнал аудита.

## Функциональность

### Каталог и направления

Приложение отображает доступные мероприятия, их статус и основные параметры. После выбора мероприятия пользователь переходит к направлениям. Направление используется как логическая единица прогресса: именно по нему рассчитываются баллы и доступность награды.

### Игры и прогресс

Для выбранного направления отображается список игр. Каждая игра имеет состояние: не начата, в процессе или завершена. После прохождения заданий обновляется прогресс участника и состояние игровой сессии.

### Игровая сессия

Игровая сессия хранит состояние прохождения конкретной игры: текущий вопрос, выбранный ответ, результат отправки, переход к следующему заданию и итоговый статус.

Поддерживаемые игровые механики:

- `question_answer` - текстовый ответ;
- `quiz` - выбор варианта ответа.

### QR/redeem-награда

Награда выдается через двухэтапный процесс:

1. Участник получает QR-код или redeem-код.
2. Стендист выполняет проверку и подтверждает выдачу.

Такой сценарий снижает риск повторной или ошибочной выдачи, поскольку сам факт отображения QR-кода не равен факту получения приза.

### Административный контур

Административный интерфейс позволяет подготовить мероприятие к запуску: настроить основные параметры, направления, игры и правила наград. Проверка готовности к публикации помогает не опубликовать неполное мероприятие.

## Технологический стек

Основные технологии:

- **Next.js App Router** - маршрутизация, структура приложения, сборка;
- **React** - построение пользовательских интерфейсов;
- **TypeScript** - строгая типизация DTO, ролей, состояний и API-контрактов;
- **TanStack React Query** - работа с серверным состоянием, кэширование и обновление данных;
- **Zustand** - локальное состояние пользовательского участия;
- **zod** - runtime-валидация критичных ответов backend API;
- **react-hook-form** - формы и валидация пользовательского ввода;
- **qrcode.react** - генерация QR-кода награды;
- **ZXing Browser** - считывание QR-кода в сценарии стендиста;
- **Tailwind CSS** - стилизация интерфейса;
- **Playwright** - e2e smoke-проверки;
- **Node.js test runner + tsx** - unit/integration-проверки TypeScript-модулей.

## Архитектура проекта

Проект построен по модульному принципу.

```text
t-events-frontend/
├── src/
│   ├── app/             # маршруты Next.js App Router
│   ├── components/      # переиспользуемые UI-компоненты
│   ├── features/        # предметные feature-модули
│   └── lib/             # инфраструктурный код
├── tests/               # unit/integration-тесты
├── e2e/                 # Playwright smoke-тесты
├── docs/                # проектная и презентационная документация
├── scripts/             # вспомогательные скрипты
├── public/              # статические файлы
├── Dockerfile
└── docker-compose.yml
```

### `src/app`

Содержит маршруты, страницы и route-level состояния:

- `loading.tsx`;
- `error.tsx`;
- `not-found.tsx`;
- страницы участника, стендиста, администратора и авторизации.

### `src/features`

Содержит предметные модули:

- `auth` - авторизация, сессия, роли;
- `events` - мероприятия, направления, игры, игровые сессии;
- `reward` - QR/redeem-награды и выдача;
- `admin` - административный контур;
- `participation` - модель участия и прогресса.

### `src/components`

Переиспользуемые компоненты интерфейса: layout, элементы навигации, кнопки, состояния загрузки, ошибки и другие UI-примитивы.

### `src/lib`

Инфраструктурный слой:

- API-клиент;
- типы данных;
- query keys;
- маршруты;
- работа с токенами;
- общие утилиты.

Ключевой архитектурный принцип - вынос логики пользовательских сценариев в `features`, чтобы страницы оставались точками композиции, а не местом хранения всей бизнес-логики.

## Интеграция с backend API

Frontend работает с backend через централизованный API-клиент. Он отвечает за:

- передачу credentials;
- обработку авторизации;
- обработку CSRF/refresh-сценариев;
- преобразование ошибок API в пользовательские сообщения;
- повтор исходного запроса после успешного обновления access token;
- runtime-проверку критичных ответов через `zod`.

### Основные endpoint-группы

Участник:

- получение списка мероприятий;
- получение деталей мероприятия;
- получение направлений;
- получение списка игр по направлению;
- старт или продолжение игровой сессии;
- получение состояния игровой сессии;
- отправка ответа;
- получение прогресса;
- получение статуса награды.

Стендист:

- preview QR/redeem-кода;
- подтверждение выдачи;
- просмотр инвентаря и выдач.

Администратор:

- управление мероприятиями;
- управление направлениями;
- управление игровым контентом;
- проверка готовности к публикации;
- публикация и архивирование;
- просмотр audit logs.

## Переменные окружения

Пример находится в `.env.example`.

```env
BACKEND_API_ORIGIN=http://localhost:8080
```

### `BACKEND_API_ORIGIN`

Адрес backend API, который используется Next.js rewrites и серверной частью frontend-приложения.

Значение по умолчанию для локального запуска:

```text
http://localhost:8080
```

Для Docker по умолчанию используется:

```text
http://host.docker.internal:8080
```

## Локальный запуск

Требования:

- Node.js 20 или новее;
- npm;
- запущенный backend API.

Установка зависимостей:

```bash
cd t-events-frontend
npm ci
```

Настройка окружения:

```bash
cp .env.example .env.local
```

Для PowerShell можно создать файл `.env.local` вручную или через команду:

```powershell
Copy-Item .env.example .env.local
```

Запуск dev-сервера:

```bash
npm run dev
```

По умолчанию приложение будет доступно по адресу:

```text
http://localhost:3000
```

## Запуск через Docker

Backend должен быть доступен до запуска frontend-контейнера.

Запуск со значением backend по умолчанию:

```bash
docker compose up --build
```

По умолчанию compose использует:

```text
http://host.docker.internal:8080
```

Это работает в Docker Desktop на Windows и macOS. На Linux в `docker-compose.yml` добавлен `host.docker.internal` через `host-gateway`.

Запуск с другим адресом backend:

```bash
BACKEND_API_ORIGIN=http://localhost:8080 docker compose up --build
```

PowerShell:

```powershell
$env:BACKEND_API_ORIGIN="http://localhost:8080"
docker compose up --build
```

## Тестирование

В проекте используются два уровня проверок.

### Unit/integration-тесты

Расположены в `tests/` и запускаются через Node.js test runner с `tsx`.

Покрывают:

- API-клиент;
- авторизацию и роли;
- маршруты;
- DTO и runtime-контракты;
- модель участия;
- игровую сессию;
- прогресс;
- награды;
- QR/redeem-сценарии;
- административные сценарии;
- audit logs;
- UI-примитивы.

### E2E smoke-тесты

Расположены в `e2e/` и запускаются через Playwright.

Основной файл:

```text
e2e/app.smoke.spec.ts
```

Smoke-тесты проверяют, что приложение стартует и ключевые страницы доступны в браузере.
